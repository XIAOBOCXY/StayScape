# StayScape 当前状态与代码审查

审查日期：2026-10-01  
部署目录：`/opt/StayScape`  
分支：`codex/productize-skill-knowledge`

## 1. 当前状态

StayScape 是面向旅居酒店与游客的文旅产品运营平台。当前运行栈包含 Vue 前端、FastAPI 服务、PostgreSQL、OpenClaw Agent 与 Nginx。游客可浏览产品并通过旅居助手匹配方案；酒店运营方可管理产品、资源、知识条目并使用 AI 生成/改写方案。在线健康检查返回数据库正常、Agent provider 为 OpenClaw；容器均为 healthy。

本轮重点把策划型知识作为有边界的参考资料接入游客咨询和产品生成，把游客回答的来源状态展示出来，并对产品工作台卡片、游客产品卡片、旅居助手对话层级、按钮和表格密度做了可见调整。知识中的案例和宏观资料不被当成实时经营事实；当前 POI 数据仍需运营人员复核。

## 2. 功能入口及调用链

| 用户入口 | API / 服务路径 | AI / Skill 与校验 |
| --- | --- | --- |
| 游客旅居助手 | 前端 `VisitorAssistant.vue` → `POST /api/v1/visitor/consult`（另有 `/recommend` 结构化入口） | 解析本轮及最近游客表达、查可用产品和运营知识 → `AgentOrchestrator.match_visitor()` → OpenClaw 的游客匹配 Skill → `VisitorAgentOutput` schema 校验 → API 对候选排序、生成追问和来源链接 |
| 游客产品目录/详情 | `/api/v1/visitor/products`、产品日期/房型/替代项等接口 | 从产品与库存数据读取；这是确定性查询路径，不由 Skill 自行编造库存 |
| 酒店产品生成 | 前端产品生成工作台 → `POST /api/v1/hotel/products/generate` → `ProductService` | 准备房型、日期、资源、天气、运营洞察、事实知识和策划上下文 → `generate_product()` → 产品生成 Skill → 结构化输出 → 服务端资源白名单、成本/价格、容量、年龄、天气与时段校验；提案须运营确认 |
| 营销文案再生成 | `POST /api/v1/hotel/products/{id}/marketing-assets` | `ProductService.regenerate_marketing_assets()` → 营销写作 Skill；产品实际库存与价格仍以服务端记录为准 |
| 酒店知识管理 | `GET /knowledge`、`POST /knowledge/refresh`、`POST /knowledge/{id}/verify` | 管理 SQL 知识项与验证状态；策划 JSON 当前是只读文件上下文，尚未纳入该管理界面 |
| OpenClaw 工具/运营入口 | OpenClaw 安装的运营及 ClawHive 工具 Skill | 可提供工具侧运营能力；浏览器产品生成流程的主入口实际是 FastAPI `ProductService`，不是网站把每个请求直接路由到运营 Skill |

Agent 由 `apps/server/app/agent/orchestrator.py` 统一调用。输入输出有 Pydantic schema，网络错误可重试，格式错误按配置尝试 JSON 修复；每次调用记录 Skill、输入/输出、状态、耗时、重试数与 fallback 状态。OpenClaw live 未就绪时会拒绝并留诊断记录，不应把 Mock 回答误作线上模型结果。

## 3. Skills 清单与职责

仓库当前有五个 `SKILL.md`：

| Skill | 作用 | 实际触发方式 / 状态 |
| --- | --- | --- |
| `stayscape-visitor-matcher` | 依据游客偏好匹配旅居方案、解释取舍、追问必要条件 | 网站 `/visitor/consult` 经 AgentOrchestrator 触发；为主要游客对话 Skill |
| `stayscape-product-generator` | 从酒店真实资源生成待审核产品草案 | 酒店产品生成 API → `ProductService` → AgentOrchestrator 触发；服务端随后作规则校验 |
| `stayscape-marketing-writer` | 生成或刷新产品营销资产 | 产品 marketing-assets API 触发 |
| `yusuchengjing-hotel-ops` | 酒店运营和文旅策划参考、运营工作流 | OpenClaw 中提供运营侧指引；网站主要生成/分析链路由服务类显式执行，Skill 路由与网站入口仍有职责边界需要进一步梳理 |
| `stayscape-clawhive-chat` | ClawHive / OpenClaw 工具协作入口 | 通过 `/api/v1/agent-tools` 等工具接口调用；与游客浏览器助手对话不同 |

建议之后为每个 Skill 固定：输入合同、输出 schema、可用工具及权限、事实等级、错误/降级策略、版本号、示例和回归用例；并在运营界面展示 Skill 版本和最近调用诊断。避免同一业务同时存在无法解释的两条路由。

## 4. 游客问答生成链路审查

1. 浏览器向 `/consult` 提交当轮问题、可选结构化条件和对话标识。前端会把最近五条游客表达合并为最多约 1000 字的自然语言上下文。
2. 后端解析出行条件并查询数据库中的有效产品/可售状态以及酒店知识。当前对话历史是轻量的用户消息上下文；不构成可靠的长期画像，刷新页面后浏览器会话也不会完整恢复。
3. 后端读取 `tourism_context.json` 的宏观、在地、标杆与工作流参考，并按问题匹配最多四条公开 POI；最多五条知识来源以 `evidence_sources` 返回。
4. Visitor Skill 要求保留累积偏好、不重复询问已有信息、缺少关键槽位时才追问、不填充凑数推荐、说明事实与取舍，不能臆造票价、开放时间或车程。
5. 模型返回受 schema 约束的结果。API 对产品候选进行再次整理，并给出最多两个动态追问；前端展示简短回答、产品卡片、核验状态和来源链接。

优点：Skill 有业务边界、输出受 schema 约束、建议经过服务端再排序、来源状态可以显示，且本轮移除了容易诱发虚构固定场次/车程的提示模板。

仍需重点强化：
- 最近五条原始用户表述不是结构化、可审计的偏好状态。建议保存旅行日期、人数/儿童年龄、预算、交通方式、节奏、兴趣、饮食/无障碍等槽位，记录每项的来源轮次、置信度和用户确认状态；冲突时先澄清。
- 把“推荐理由”与具体产品事实和来源 ID 关联，避免回答中有链接但无法证明该链接支持某项具体陈述。模型应只对有证据的事实陈述下结论。
- schema 增加 `no_match_reason`、`confidence`、`missing_constraints`、`evidence_ids`、`tradeoffs` 等机器可校验字段；低置信度、知识不足、上游超时要有清晰降级分支。
- 追问策略目前主要是轻量规则，建议使用必需槽位矩阵并限制单轮问题数；若用户只要灵感，先给带假设标注的选择，避免表单式连环追问。
- 增加对话用例评估：有库存/无库存、条件冲突、连续追加偏好、雨天亲子、无障碍、信息不足、知识缺失、Agent 超时、重复/矛盾追问、事实来源过期。每个用例检查引用正确性、约束满足、追问质量和是否编造。

### 5.3 运营数据库

## 7. 审查结论与优先级

### P0：事实可靠性和来源时效

当前 25 条 POI 全部待复核；没有地图路由提供商返回的实时车程，也没有实时票务/开闭园 API。上线上线前应让运营人员逐条核对官方地址、开放时段、预约规则、价格、交通、无障碍/亲子服务及更新时间；没有数据时界面应明确表示未知，并引导官方渠道。现有策划来源含历史统计及转载页面，应设有效期和权威等级。

### P1：Skill 对话成为可控工作流

建立会话槽位与显式澄清确认状态，限制重复追问；每个推荐事实关联证据 ID；完善无匹配/低置信/工具失败降级；维护中文真实对话回归集。游客响应 schema 目前偏重结果载荷，没有足够丰富的置信度、冲突、证据映射和缺失槽位协议。

### P1：知识运营闭环

策划 JSON 尚无后台编辑、审核、版本回滚和定期失效机制，知识来源的采集、审核、发布仍依赖工程部署。建议提供知识条目后台，支持引用、采集日、责任人、状态、有效期和 diff，且发布前由运营确认。

### P1：Skill 入口与职责一致

`yusuchengjing-hotel-ops` 是运营级指导，产品网站主流程由确定性的 API/服务链调用三个细分生成 Skill。需画清“游客助手 / 酒店工作台 / OpenClaw 工具”路由图，明确哪些步骤由模型、业务服务、外部工具负责；避免一个 Skill 文档声称可做网站链路实际未触发的动作。

### P2：更多外部工具与效果评估

地图距离/导航、天气、预约票务、官方公告可按供应商可用性逐步接入；每种外部数据要有超时、缓存、来源和降级。现有产品生成接有天气/资源上下文，但游客 POI 没有实时路由与票务核验。建立评估集和 Skill 调用日志看板，按事实准确率、约束命中率、无依据陈述率、追问轮次、失败恢复率追踪。

### P2：Web 性能与视觉核验

生产构建成功，但 Vite 提示约 500 KB 的 chunk 阈值超出；代码分割路由、延迟加载图表/编辑器可降低初始下载。服务器端构建资产确认包含工作台卡片变化和新样式，服务健康正常；本轮未完成真实浏览器截图核验，故不能把静态构建当成完整视觉验收。浏览器若仍显示旧卡片，请硬刷新并核实 web 容器静态资源时间戳；下一轮应以游客页、工作台桌面/移动宽度分别截图检查溢出、卡片高度、按钮可达性和表格横向滚动。
