# 自然语言产品调整一致性设计

日期：2026-09-29

## 目标

自然语言输入每轮只修改用户明确提到的字段，未提及字段必须继承当前主推荐。无效请求不得静默换成其它值；候选产品必须完整继承最终主推荐。

## 状态更新规则

- 日期、房型、客群、人数、预算、体验、酒店服务和路线分别解析，互不推断。
- 只有明确的人群词（如“单人”“情侣”“亲子”“朋友同行”）可以改变客群与人数。体验或服务名称中的“演出”“博物馆”“咖啡”等词不能改变客群。
- 未出现新预算时沿用 `visitor_budget`；未出现新路线要求时沿用 `route_note`。
- 替换或增加体验、增加或移除酒店服务时，日期、房型、客群、人数、预算和路线均保持不变。
- 生成候选时直接使用会话中的最终主推荐，不再次推断或重置字段。

## 日期规则

- 完整日期和月日写法都先解析为用户指定日期。
- 月日早于服务器当天时视为过去日期，不自动推到下一年。
- 过去日期、超出可售范围的日期、没有对应房型库存的日期均返回结构化校验结果，保留当前主推荐。
- 校验结果包含失败原因和最多三个最近可售日期，必须由用户明确选择后才切换。
- 前端在主卡上方展示失败原因，并在操作记录中记下未生效的指令。

## 数据流

1. `ProductAdvisor._parse` 只提取本轮明确字段。
2. `respond` 将明确字段覆盖到会话状态；其余字段从上一轮状态继承。
3. 日期与房型先经过库存匹配。无法匹配时返回 `validation_error`，不进入业务重算。
4. 业务判断只组合已验证的状态，不再根据资源名称反推客群。
5. API 持久化完整主推荐，候选生成读取同一份状态。
6. 前端收到校验错误时保留主卡、显示错误与备选日期，并记录操作。

## 测试矩阵

- 日期：完整未来日期、未来月日、今天、明天、周末、过去日期、无库存日期、日期与房型不匹配。
- 客群与人数：单人、双人、亲子、朋友；价格、路线、体验、服务后续调整不得污染客群或人数。
- 预算：整数与小数、低于最低合法价、后续调整后的持续继承。
- 体验：替换、增加、移除、不存在或容量不足；其它字段保持不变。
- 酒店服务：增加、移除、不存在或库存不足；其它字段保持不变。
- 路线：轻松、自由时间要求可见，并跨后续轮次保留。
- 候选生成：日期、房型、客群、人数、预算、体验、服务、路线与最终主推荐一致；不自动发布。
- 前端：成功变更、无变化、校验失败三种结果均有清晰反馈并进入操作记录。

## 验收标准

1. 输入过去日期不会改变主推荐，并明确说明日期已过期。
2. 输入可售未来日期后，主卡和生成候选均使用该日期。
3. 替换“沉浸式城市演出”等体验不会把单人套餐改为双人。
4. 设置价格上限后再调整路线，价格约束仍然生效。
5. 连续调整后生成的每个候选与最终主推荐的核心字段一致。
6. 自动化测试覆盖上述矩阵，线上真实 HTTP 流程复测通过且不发布产品。
